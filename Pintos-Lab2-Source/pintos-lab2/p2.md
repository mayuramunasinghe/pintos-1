## Argument Passing

#### DATA STRUCTURES

>A1: Copy here the declaration of each new or changed struct or struct member, global or static variable, typedef, or enumeration.  Identify the purpose of each in 25 words or less.

No persistent argument-specific structure is added. The startup packet is shared with process creation:

```c
struct start_info {
  char *command;
  struct child_status *status;
};
```

- `command`: Private, page-sized command copy owned by the child after successful creation.
- `status`: Shared record used to report loading and eventual termination.

`start_process()` allocates one page for a temporary `char **argv` array. `argc`, the tokenizer's `save` pointer, and stack-size counters are local variables. The array is allocated off the small kernel stack and freed before entering user mode.




#### ALGORITHMS

>A2: Briefly describe how you implemented argument parsing.  How do you arrange for the elements of argv[] to be in the right order?
>How do you avoid overflowing the stack page?

`process_execute()` rejects empty commands and commands of 4096 bytes or more, copies the command, and creates the child. Leading spaces are skipped. The child tokenizes on spaces using `strtok_r()`, so repeated spaces are ignored. Only `argv[0]` is passed to the executable loader.

The argument strings are copied onto the user stack in reverse order. Their user addresses replace the corresponding temporary array entries. The code adds zero padding to a four-byte boundary, pushes a NULL sentinel, then pushes argument pointers from the last argument to the first. Finally it pushes `argv`, `argc`, and a fake zero return address. Thus `argv[0]` points to the executable name and `argv[argc]` is NULL.

Before writing anything, the implementation computes:

`required = string_bytes + alignment_padding + 4 * (argc + 4)`

The four extra words are the NULL sentinel, `argv`, `argc`, and fake return address. If the total exceeds the single 4096-byte stack page, loading fails. The temporary pointer array is also bounds-checked. Quoting and shell expansion are intentionally outside this lab's parser.




#### RATIONALE

>A3: Why does Pintos implement strtok_r() but not strtok()?

`strtok()` normally keeps its parsing position in shared static state. A context switch to another process parsing a command could overwrite that state. `strtok_r()` receives a caller-owned save pointer, allowing separate tokenizations to proceed without interfering. It is also suitable for nested tokenization when separate save pointers are used.




>A4: In Pintos, the kernel separates commands into a executable name and arguments.  In Unix-like systems, the shell does this separation.  Identify at least two advantages of the Unix approach.

Separating commands in the shell keeps policy out of the kernel: quoting, wildcard expansion, variables, and pipelines can evolve without changing privileged code. Different shells can offer different syntax while using the same process interface. Passing a prepared argument vector also avoids reparsing text in the kernel and preserves argument boundaries, including arguments that contain spaces.

>B2: Describe how file descriptors are associated with open files. Are file descriptors unique within the entire OS or just within a single process?

Each process has a linked list of `file_descriptor` entries. An entry associates an integer with a `struct file *`. Descriptors 0 and 1 are reserved for standard input and output and are handled separately. `open()` allocates numbers starting at 2. Numbers are unique only within a process, are not inherited, and are not reused during that process's lifetime.

Opening the same filename twice calls `filesys_open()` twice, producing separate file positions and independent close operations. Lookup is a linear scan. Closing removes the list entry, closes its file under the file-system lock, and frees the entry. Process exit closes every remaining descriptor.




#### ALGORITHMS

>B3: Describe your code for reading and writing user data from the kernel.

The syscall handler first validates and copies the four-byte syscall number. It determines the exact argument count and validates/copies only those argument words into a small kernel array. Return values are placed in `intr_frame.eax`.

`validate_buffer()` rejects NULL for nonempty ranges, kernel addresses, and ranges that cross `PHYS_BASE`. The range check uses subtraction before addition, preventing integer wraparound. It checks every intersected page. Input buffers require a present mapping; output buffers additionally require a writable page-table entry, checked by the new `pagedir_is_writable()` helper.

`copy_string()` walks at most 4096 bytes, checks each newly entered page, and looks for a terminator. It allocates a kernel copy only after validation. Nonterminated or oversized strings return an ordinary failure; invalid addresses terminate the process with -1.

After validation, file reads/writes use the user buffer directly under `filesys_lock`. In Project 2 there is no eviction and each process has only one thread, so the mapping cannot be removed concurrently. This would need revisiting for virtual memory or multithreaded processes. Keyboard reads use `input_getc()`; stdout writes use `putbuf()` in chunks of up to 512 bytes.




>B4: Suppose a system call causes a full page (4,096 bytes) of data
>to be copied from user space into the kernel.  What is the least
>and the greatest possible number of inspections of the page table
>(e.g. calls to pagedir_get_page()) that might result?  What about
>for a system call that only copies 2 bytes of data?  Is there room
>for improvement in these numbers, and how much?

For the data buffer alone, a 4096-byte range occupies one page when page-aligned and two pages otherwise. Therefore validation performs a minimum of 1 and a maximum of 2 page-table inspections. A two-byte range likewise needs 1 inspection normally, or 2 when it crosses a page boundary. Output-buffer permission checks are performed in the same page-table lookup by `pagedir_is_writable()`.

These counts exclude reading the syscall number and its argument words, and exclude hardware translation during the actual copy. The handler validates the number and argument block separately, so they may inspect the same page more than once.

A byte-by-byte validator would inspect 4096 times for a page-sized buffer or twice for two bytes. Checking once per intersected page removes that redundancy. For a general buffer, one or two checks are already the minimum needed to establish the mapping of every touched page. Combining adjacent syscall-header validation could reduce the separate header overhead.




>B5: Briefly describe your implementation of the "wait" system call
>and how it interacts with process termination.

`process_wait(pid)` searches only the current process's direct-child list. If no entry exists, it returns -1. Otherwise it removes that entry immediately, making repeated waits fail, and waits on its `exited` semaphore.

On termination, the child closes descriptors and its executable, releases its own child records, destroys its address space, stores its exit value, and signals `exited`. The parent reads the retained value and releases its reference. The child also releases its own reference. The shared status record can outlive the child's `struct thread`, so an already-exited child's result remains available.

The syscall delegates to `process_wait()`. The initial process also uses the existing kernel call to this function, preventing shutdown before that process finishes.




>B6: Any access to user program memory at a user-specified address
>can fail due to a bad pointer value.  Such accesses must cause the
>process to be terminated.  System calls are fraught with such
>accesses, e.g. a "write" system call requires reading the system
>call number from the user stack, then each of the call's three
>arguments, then an arbitrary amount of user memory, and any of
>these can fail at any point.  This poses a design and
>error-handling problem: how do you best avoid obscuring the primary
>function of code in a morass of error-handling?  Furthermore, when
>an error is detected, how do you ensure that all temporarily
>allocated resources (locks, buffers, etc.) are freed?  In a few
>paragraphs, describe the strategy or strategies you adopted for
>managing these issues.  Give an example.

User-access checking is concentrated in `validate_buffer()`, `copy_string()`, and the initial syscall-word copying. This keeps the dispatch cases readable and ensures common rules apply consistently. Invalid user memory calls `bad_user()`, which sets exit status -1 and terminates through the normal process cleanup path.

Validation is done before acquiring `filesys_lock`. String copying validates before allocation; no later user-pointer access is necessary after the kernel copy exists. Consequently, a bad pointer cannot leave the global file-system lock held or leak a partially allocated string. Each normal operation releases its lock before returning. Failed descriptor allocations or opens free their temporary entries.

For example, `write(fd, buffer, size)` first validates the complete buffer, including its last page. Only then does it find the descriptor and acquire the file-system lock. If the last page is invalid, the process exits before entering the critical section. If the descriptor is invalid, the call returns -1. All already-open files are reclaimed by `process_exit()` when the process terminates.

The executable loader uses a common `done` path to close its temporary file on failure. Startup frees the command page and argument-pointer page on both success and failure. A failed `thread_create()` frees the startup packet, command page, and status record in the parent.




#### SYNCHRONIZATION

>B7: The "exec" system call returns -1 if loading the new executable
>fails, so it cannot return before the new executable has completed
>loading.  How does your code ensure this?  How is the load
>success/failure status passed back to the thread that calls "exec"?

The parent creates a status record with `loaded` initialized to zero and passes that record to the child through `start_info`. After creating the thread and recording its tid, the parent executes `sema_down(&status->loaded)`.

The child completes ELF loading and argument-stack construction, writes `load_ok`, and executes `sema_up(&status->loaded)` on every startup outcome. The parent then returns the tid only if `load_ok` is true. Otherwise it removes the record from its child list, releases its ownership, and returns -1. A semaphore remembers an early signal, so the child may finish loading before the parent starts waiting. No file-system lock is held while waiting for a child.




>B8: Consider parent process P with child process C.  How do you
>ensure proper synchronization and avoid race conditions when P
>calls wait(C) before C exits?  After C exits?  How do you ensure
>that all resources are freed in each case?  How about when P
>terminates without waiting, before C exits?  After C exits?  Are
>there any special cases?

There are two initial references to each status record: one for the parent and one for the child. Only the parent manipulates its own child list. Reference decrements are protected by disabling interrupts briefly, which is appropriate for this single-CPU Pintos kernel. The record is freed only when the count reaches zero.

- Parent waits before child exits: the parent removes the list entry and blocks. The child completes cleanup, publishes status, and signals. Both release their references.
- Child exits before parent waits: the child releases its reference; the parent's reference keeps the status and signaled semaphore alive. A later wait returns immediately.
- Parent exits first without waiting: parent cleanup removes all child entries and releases those references. A surviving child still owns its record and frees it on exit.
- Child exits first and parent never waits: the record remains until parent cleanup releases its final reference.
- Invalid/nonchild/repeated wait: no record is found, so -1 is returned without blocking.
- Load failure: the parent releases its reference after the load notification; child termination releases the other, regardless of scheduling order.
- Thread creation failure: no child exists, so all startup resources are freed directly.

The child's thread and address space are not retained merely to preserve an exit value. Children are not reparented or inherited.




#### RATIONALE

>B9: Why did you choose to implement access to user memory from the
>kernel in the way that you did?

Explicit validation keeps error handling in ordinary C and avoids making kernel page faults recoverable. It checks permission as well as presence before reading into user buffers, protecting read-only code pages. Page-based checks reduce redundant page-table walks compared with validating every byte.

The tradeoff is a separate validation pass before I/O. Its safety relies on the Project 2 assumptions: stable mappings, no eviction, and one thread per process. A future VM implementation would need page pinning or another protected-copy mechanism. The 4095-character command/string limit is an explicit resource bound, not a general Unix limit.




>B10: What advantages or disadvantages can you see to your design
>for file descriptors?

The linked list uses memory in proportion to the number of open files, avoids a large fixed array inside `struct thread`, and has no small artificial descriptor-table limit. Each open has a separate file object. Monotonic numbering is simple and avoids immediately recycling stale descriptor numbers.

The costs are O(n) lookup and a separate allocation per descriptor. A long-lived process that repeatedly opens and closes files can exhaust the monotonic integer namespace; the implementation refuses allocation before signed overflow. A dynamically grown indexed table could provide faster lookup and reuse numbers, at the cost of additional table management.




>B11: The default tid_t to pid_t mapping is the identity mapping.
>If you changed it, what advantages are there to your approach?

The identity mapping is retained: the pid returned by `exec()` is the child's `tid_t`. This lab uses one thread per user process, so a second identifier allocator and mapping table would add bookkeeping without a practical benefit. Parent-child validation is performed using the parent's status list, rather than assuming that any existing tid is a valid child.
